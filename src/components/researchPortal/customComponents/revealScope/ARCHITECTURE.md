# REVEAL SCOPE — architecture

Technical overview and source specification for **REVEAL SCOPE** in dig-dug-portal. For UI conventions and product/session rules as they are decided, see [`DESIGN.md`](./DESIGN.md).

The root shell is **`../revealScope.vue`** (registered as `reveal-scope`, portal `"component": "revealScope"`). Sub-components and utility modules for this project live in this directory (`revealScope/`), following the same pattern as `revealKgWorkspace/` (REVEAL KG Canvas).

**Status:** scaffold only. The shell currently renders a header and an empty stage. Hub + Modules A–D below are not yet implemented — this document is the design contract for that build.

## Source specification (v1.0, approved for development)

> The section below is the architecture spec as approved, preserved verbatim as the source of truth. Do not silently edit it in place — record any change as a new dated entry in the Changelog at the bottom of this file, and update the spec text itself only when the change is confirmed with the product/architecture owner (see §8 for the two items still open).

**Status:** Approved for development, with 2 flagged open decisions (see §8).
**Product:** SCOPE (hypothesis evaluation workbench) — one product within the **REVEAL fleet**, alongside DESIGN (downstream analytical workspace system). DESIGN has its own spec and is referenced here only at the handoff boundary.

**A naming note for readers of this doc:** "SCOPE" (the product name) and "scope" (the ordinary English word describing coverage boundaries — e.g. *scope-bounded gap metadata*, *out of scope*) both appear frequently below and mean different things. Product name is always capitalized as SCOPE; the coverage concept is lowercase.

### 1. Purpose

SCOPE takes a free-text biological hypothesis and helps a researcher determine two independent things:

1. **Is the hypothesis well-formed?** (structural/logical quality — testability, precision)
2. **What do we actually know about it?** (evidential grounding — what curated knowledge graphs support, contradict, or are silent on)

SCOPE does **not** attempt to resolve every hypothesis. Its core product principle is:

> **Bounded honesty:** the system answers only as much as it knows, states its coverage explicitly, and never lets a fast or confident-looking result imply more certainty than was actually established.

This principle is not a feature of one module — it is a cross-cutting constraint every module must satisfy (see §7).

### 2. Architectural Model: Hub-and-Spoke Workbench

SCOPE is **not** a linear pipeline. It is a shared-state hub with four independent, on-demand modules. A user may invoke any subset of modules, in any order, without waiting on the others.

```
                  [ Free-Text Input ]
                           │
                           ▼
           ┌───────────────────────────────┐
           │ CENTRAL HYPOTHESIS STATE HUB  │
           │ (Parsed Slot JSON Schema)     │
           └───────────────┬───────────────┘
                           │
    ┌──────────────────────┼──────────────────────┬──────────────────────┐
    ▼                      ▼                      ▼                      ▼
┌──────────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│  MODULE A:   │    │  MODULE B:   │    │  MODULE C:   │    │  MODULE D:   │
│  Quality &   │    │  Literature  │    │  KG Evidence │    │  Dataset &   │
│  Syntax      │    │  Handoff     │    │  Path Finder │    │  Workspace   │
└──────────────┘    └──────────────┘    └──────────────┘    └──────────────┘
 (Real-time)         (Instant UI)        (Async Graph)       (On-demand)
```

**Design rule:** the hub is parsed exactly once per session. All four modules read from the same hub state and never re-parse independently. This prevents drift between modules interpreting the same hypothesis differently.

### 3. Core Data Model: Central Hypothesis State

The hub converts free text into a structured, versioned JSON object. This is the single source of truth for all modules.

```json
{
  "hypothesis_id": "uuid",
  "schema_version": "1.0",
  "raw_text": "string, original user input, never mutated",
  "parsed_at": "ISO-8601 timestamp",
  "slots": {
    "target": { "value": "string", "confidence": "high|medium|low", "resolved_id": "canonical ID or null" },
    "perturbation": { "value": "string", "confidence": "high|medium|low", "resolved_id": "canonical ID or null" },
    "outcome": { "value": "string", "confidence": "high|medium|low", "resolved_id": "canonical ID or null" },
    "modifiers": {
      "cell_line": { "value": "string|null", "confidence": "high|medium|low" },
      "genetic_background": { "value": "string|null", "confidence": "high|medium|low" },
      "dose_timepoint": { "value": "string|null", "confidence": "high|medium|low" },
      "tissue": { "value": "string|null", "confidence": "high|medium|low" },
      "comparator": { "value": "string|null", "confidence": "high|medium|low" }
    }
  },
  "parse_confidence_overall": "high|medium|low",
  "missing_required_slots": ["array of slot names, empty if none"],
  "hub_version": "integer, incremented on any user edit"
}
```

**Notes for implementation:**
- `modifiers` is an **open, extensible map** — new modifier types can be added without a schema migration breaking existing hypotheses. Do not hardcode a fixed triple; treat `target`/`perturbation`/`outcome` as required, everything else as optional and expandable.
- `resolved_id` fields are populated by entity linkage (Ensembl, MONDO, ChEMBL, etc.) and may be `null` if resolution failed — this is a valid, expected state, not an error.
- `hub_version` is the mechanism that powers staleness detection (§7.1). Every module output must record which `hub_version` it was computed against.

### 4. Module Specifications

#### Module A — Quality & Syntax Panel
**Execution:** synchronous, real-time, runs on every hub update.

| | |
|---|---|
| **Input** | Hub state |
| **Output** | Multi-axis rubric (Precision, Falsifiability — no scalar/composite score), completeness warnings, slot inspector view |
| **Key behaviors** | 1. **Slot Inspector toggle**: user can view and manually correct any parsed slot before it propagates downstream. 2. Any axis the system cannot confidently evaluate must render as **"unscored — insufficient basis"**, never a forced/default rating. 3. Runs instantly; never blocks on Modules B/C/D. |

#### Module B — Literature Launcher
**Execution:** synchronous, instant.

| | |
|---|---|
| **Input** | Hub state |
| **Output** | Editable Boolean query strings / prompts, deep links (PubMed, etc. — non-commercial sources only, see Changelog 2026-09-03) |
| **Key behaviors** | 1. Generated queries are **shown and editable** before the user clicks through — never a black box. 2. This module is an **isolated human-trust lane**. Its results are never written into the Evidence Matrix (Module C's output) and never assert findings on the system's behalf. It hands the user off to external tools and gets out of the way. |

#### Module C — KG Evidence & Path Explorer
**Execution:** asynchronous, background job, renders incrementally as data arrives.

| | |
|---|---|
| **Input** | Hub state (resolved slot IDs) |
| **Output** | Evidence Matrix: per hypothesis-element and per hop, one of `VERIFIED`, `REFUTED`, `CONFLICT`, `UNEXPLORED`; scope-bounded coverage metadata per KG queried |
| **Key behaviors** | 1. **Constrained LLM Query Planner**: LLM is used only to draft graph queries (Cypher/SPARQL), which are validated against canonical KG schemas before execution. LLM never generates evidentiary claims directly. 2. **Path Completeness** is reported as explicit per-hop state, never a collapsed ratio (e.g. not "2/3" — instead "hop 1: VERIFIED, hop 2: UNEXPLORED, hop 3: VERIFIED"). 3. **Coverage metadata is mandatory** on every result: `[KG name, version, scope, last updated]`. Absence must always read as "not found in [named, scoped source]," never as an unqualified "does not exist." 4. **UNEXPLORED vs. no-data-yet-loaded must be visually unambiguous** — see §7.2. 5. Evidence sourced here is the **only** input to what would become a Tier 1 evidence designation (see §6 — tiering itself is deferred, but this module's output is the only category eligible for it later). |

#### Module D — Dataset & Workspace Provisioner
**Execution:** on-demand, triggered explicitly by the user (evaluation → action transition).

| | |
|---|---|
| **Input** | Hub state + user-selected gap(s) from Module C |
| **Output** | MCP payload, one of two paths |
| **Key behaviors** | 1. **Path A (data exists, unlinked):** direct handles to existing GEO/SRA/etc. accessions. 2. **Path B (true absence — no data exists anywhere indexed):** protocol/pipeline template for generating new data. **Path B is not a lesser/deferred case — it is the more differentiating capability of this module and must not be scoped out in favor of only building Path A.** 3. Output is packaged for handoff to the DESIGN system's analytical workspace. |

### 5. Module Interaction Rules

- Modules **A, B, C, D read from the hub independently.** No module calls another module directly.
- Module C and D are the only modules with async/long-running execution. A and B must never be gated behind them.
- The **only mandatory sequencing** is: the hub must have completed its initial parse before any module can run. Beyond that, order is entirely user-driven.

### 6. Explicitly Out of Scope for v1 (deferred, not forgotten)

These were raised during design and intentionally excluded from this build. Do not implement speculatively; do not let them silently expand v1 scope.

| Item | Status | Note |
|---|---|---|
| Novelty / redundancy check (has this hypothesis been tested before?) | Excluded by product decision | Not a target feature. |
| Corroboration weighting within evidence (independent studies vs. shared root source) | Excluded by product decision | Not a target feature. |
| Tier 1 (curated) vs. Tier 2 (in-house/experimental) evidence separation | Deferred | Only becomes relevant once a bi-directional feedback loop exists. Build the tiering model **before** the first write-back ships if/when this is picked up — do not retrofit onto a matrix users already read as uniform. |
| Bi-directional feedback loop (DESIGN results writing back into SCOPE's evidence matrix) | Deferred | No feedback loop exists in this build. |
| Cross-KG relation-vocabulary conflict resolution (e.g. `inhibits` vs `downregulates` across KGs) | Not applicable per current KG set | The federated KGs in scope have non-overlapping domains, so cross-KG relation conflicts are not expected to occur in practice. See §8 for the related open item on entity linkage across domain boundaries. |
| DESIGN's "one schema for any hypothesis type" / paper-mining-to-hypotheses / semantic embedding matching against all CFDE datasets | Explicitly rejected as v1 premise | Assessed as overreaching given current data and unproven generalization. If pursued later, treat as a separate, narrow, empirically-validated extension — not a foundational assumption baked into SCOPE's schema. |

### 7. Cross-Cutting Requirements (apply to every module)

#### 7.1 Staleness / Session Model
- The hub increments `hub_version` on any user edit to a slot.
- When `hub_version` changes after a module has already rendered output, that module's panel must **raise a visible flag** to the user rather than silently continuing to display now-outdated results.
- **Default recommended behavior** (confirm with product before building): completed module panels are archived as read-only/labeled-stale rather than hard-deleted, and only modules affected by the changed slot are prompted for re-run. Full hard session reset is the simpler fallback if selective recompute proves complex — but this is a real trade-off (see §8, item 2) and should be a deliberate choice, not a default nobody decided.

#### 7.2 Loading vs. Empty-Result Ambiguity
- Every async module (primarily Module C) must expose an explicit state machine, not an implicit one:
  - `PENDING` (query in flight)
  - `COMPLETE_NO_RESULTS` (query finished, genuinely nothing found)
  - `COMPLETE_WITH_RESULTS`
- `PENDING` and `COMPLETE_NO_RESULTS` must be visually distinguishable at a glance (e.g. spinner/skeleton vs. an explicit "nothing found in [scope]" state). A user must never be able to mistake an in-flight query for a confirmed null result.
- `COMPLETE_NO_RESULTS` must render as a flat factual statement of absence, scoped to what was queried. It must **never** be reworded or interpreted (e.g. never rendered as "this appears novel" or similar). This is a hard rule for both UI copy and any LLM-generated summary text.

#### 7.3 Confidence Propagation
- Every module output must carry a reference to the `parse_confidence_overall` and `hub_version` it was computed against.
- If a downstream module (B, C, D) operates on a slot with `confidence: low`, that module's UI must visibly carry a "based on low-confidence extraction" flag rather than presenting its output as equally authoritative to a high-confidence run.

#### 7.4 Grounding Discipline (Module C specifically)
- No evidentiary claim may be presented without a resolvable, clickable source (KG edge ID, PMID, GEO accession, canonical entity ID).
- The LLM is permitted to *summarize* retrieved subgraphs but every sentence of that summary must be traceable back to a specific retrieved edge. Underlying edges should be shown alongside any LLM summary, not hidden behind it.

### 8. Open Decisions — Flagged for Resolution Before/During Build

These two items came up during design and were **not** resolved with a definitive answer. Do not let a default implementation choice silently settle them — raise back to product/architecture owner.

**1. Module C "CONFLICT" state — exact trigger condition.**
Given that the federated KGs in scope have non-overlapping domains (per product decision, §6), cross-KG relation conflicts are not expected. This raises the question: what does `CONFLICT` actually mean now?
- Is it intra-KG (two different source studies within the *same* KG asserting opposite relations for the same edge)?
- Is the state still needed at all in v1, or should it be removed until a concrete triggering scenario exists?
**Recommendation:** do not build a `CONFLICT` state handler speculatively. Confirm a real triggering scenario exists in the current KG set before implementing it; otherwise ship v1 with three states (`VERIFIED`, `REFUTED`, `UNEXPLORED`) and add `CONFLICT` later if a concrete case arises.

**2. Entity linkage across KG domain boundaries for multi-hop path stitching.**
"Non-overlapping domains" resolves the relation-vocabulary conflict problem, but a multi-hop hypothesis may still need to traverse a shared entity that sits at the boundary between two KGs (e.g. a gene node that is a hop-endpoint in KG-Oncology and a hop-start in KG-Pathways). This requires consistent entity ID resolution across KG boundaries even if the KGs never disagree on a relation.
**Needs an explicit answer before Module C's multi-hop traversal logic is built:** does SCOPE's current KG set ever require paths to cross KG boundaries at all? If yes, entity resolution across boundaries is required scope for Module C. If no (each hypothesis is fully answerable within a single KG's domain), this can be deferred.

### 9. Recommended Build Sequencing

1. **Hub + Module A** — parsing, extensible schema, slot inspector, rubric. No external dependencies; fastest path to a usable, testable core.
2. **Module C (core)** — start with a narrow KG scope (2–3 KGs where domain non-overlap is already confirmed), implement `VERIFIED`/`REFUTED`/`UNEXPLORED` first, resolve open decision #2 before building multi-hop traversal, defer `CONFLICT` per open decision #1.
3. **Module B** — low complexity, mostly UI/query-string generation; can be built in parallel with Module C at low risk.
4. **Module D** — build Path A (existing data handles) and Path B (generation protocol templates) as explicitly separate flows from the start; do not let Path B slip to "later" — it is the more differentiating capability.
5. **Cross-cutting staleness and confidence-propagation UI** (§7.1, §7.3) should be implemented alongside Module A/C, not retrofitted after — these are cheap to build in from the start and expensive to bolt on later.

### 10. Explicit Non-Goals (state to avoid scope creep)

- SCOPE does not generate novel scientific claims. It structures, scores, and checks a user-provided claim against existing curated knowledge.
- SCOPE does not judge fair use, novelty, or publishability.
- SCOPE does not perform its own literature text-mining or relation extraction from free text (Module B is deep-link handoff only).
- SCOPE does not attempt to support arbitrary hypothesis types beyond the gene/perturbation/outcome-and-modifiers domain in v1.

**No Central Hypothesis State Hub exists yet.** Both `ScopeLiteratureLauncher` and `ScopeEvaluationPanel` currently take raw `hypothesisText` as a prop directly from the welcome panel's option cards — neither reads hub slots, carries `hub_version`/`parse_confidence_overall` (§7.3), or is staleness-aware (§7.1). This is a deliberate v0 shortcut, not the spec-conformant Module A/B; revisit both once the hub is built (§3) so they read from hub state like the spec requires.

**Module B v0 behavior:** on mount, calls an LLM (`scopeLiteratureQuery.js`, via `src/utils/llmClient.js`) to extract a concise search-term string from the hypothesis text, prefills one editable text box for PubMed (`scopeLiteratureSources.js`), and opens the built URL in a new browser tab on click. On LLM failure, silently falls back to the raw hypothesis text as the query (logged to console, no user-facing error). No results are captured or written back — once the tab opens, SCOPE's involvement ends, matching the spec's "isolated human-trust lane" rule (§4 Module B, §5).

**Module A v0 behavior:** on mount, calls an LLM (`scopeHypothesisEvaluation.js`) that both parses the hypothesis into slots and scores Precision/Falsifiability in one pass (a v0 shortcut — real Module A only scores, the hub only parses; here they're combined because there's no hub to parse first). Output shape mirrors §3's Central Hypothesis State (`target`/`perturbation`/`outcome`/`modifiers`, each `{value, confidence}`) so it's a drop-in once the hub exists. Any axis the model can't confidently score renders literally as "Unscored — insufficient basis" (never a forced/default rating, per §4 Module A behavior 2) — enforced structurally via a `scored: boolean` field, not left to prose. Missing required slots (`target`/`perturbation`/`outcome`) surface as an orange pill callout (DESIGN.md sub-header callout pattern). **Known gap:** the spec's Slot Inspector (§4 Module A behavior 1 — user can view *and manually correct* any parsed slot) is not implemented; slots currently render read-only. On total LLM failure, renders explicit unscored state with rationale "Evaluation could not be completed" rather than silently faking a result — no fallback-to-raw-text is possible here (unlike Module B) since evaluation *is* the LLM call.

**Module C v0 query layer:** built against the real Proto-OKN CFDE REVEAL KG, reusing the same endpoint `biomarkerNetwork.vue` already queries (`https://apps.okn.us/digcfdekg/sparql`, named graph `https://purl.org/okn/frink/kg/digcfdekg`) via a self-contained client (`scopeKgSparql.js` — deliberately does not import `biomarkerNetwork/cfdeKgSparql.js`, to keep SCOPE's product tree independent of that sibling component). This is a **statistically-inferred association graph** (GWAS/expression-factor-derived weights: predicates `geneToTrait`, `geneToFactor`, `traitToFactor`, `geneInGeneSet`, `geneSetToTrait`, each carrying a `weight` via RDF reification), not a curated causal/mechanistic KG — there is no directional "inhibits"/"activates" relation type, so per user decision this KG supports only `VERIFIED`/`UNEXPLORED` in v1, never `REFUTED` or `CONFLICT` (extends the reasoning in the already-recorded §8 open decision #1, though that item's original text is left as-is since it's framed product-wide, not KG-specific).

`findKgEvidence({ targetText, targetResolvedId, outcomeText, outcomeResolvedId, onStep })` in `scopeKgEvidence.js` runs three evidence routes — always all three, never short-circuited on an earlier match, so each gets its own explicit state per the spec's per-hop reporting rule (§4 Module C behavior 2):
1. **Direct** (`hop: 1`) — `geneToTrait` edge straight from the target gene to a matching trait.
2. **Shared factor** (`hop: 2`) — target gene links to a `Factor` node that is *semantically* resolved from the outcome text (see below).
3. **Gene set membership** (`hop: 3`) — target gene's `GeneSet` (`geneInGeneSet`) links to the trait (`geneSetToTrait`).

These are **evidence routes of increasing indirection, not literal hops of one mechanistic path** — the spec's hop example (target→intermediate→outcome) assumes a walkable causal chain, which this association graph doesn't model. Framed and documented as such rather than silently overclaiming the spec's original hop semantics.

**Entity resolution problem, found via a real user test case (2026-09-04):** a hypothesis about Pembrolizumab/PD-1/IFN-gamma secretion evaluated cleanly (Precision/Falsifiability both "High", no missing slots) but returned zero results on all three routes. Root cause, confirmed against the live endpoint: this KG indexes genes under their **official HGNC symbol only** — "PD-1" has zero `geneToTrait`/`geneToFactor` edges, "PDCD1" has hundreds — and the outcome side has the deeper problem that outcome text is usually a **mechanism-level phrase** ("IFN-gamma secretion") with no matching Trait node to find by substring at all; Trait nodes are diseases/phenotypes, not lab readouts.

Two-part fix:
1. **Gene side — `resolved_id`:** ARCHITECTURE.md §3's Central Hypothesis State schema already defined `resolved_id` on `target`/`perturbation`/`outcome` ("canonical ID or null") — v0 had just never populated it. `scopeHypothesisEvaluation.js`'s prompt now instructs the LLM to fill `target.resolved_id` with the official HGNC gene symbol when confident (e.g. `"PD-1"` → `"PDCD1"`, `"Pembrolizumab"` → `"PDCD1"`, the gene the drug targets) and `outcome.resolved_id` with a canonical disease/phenotype name when one exists, `null` otherwise — never forced. `scopeKgEvidence.js` prefers `resolvedId` over raw `value` for the gene-label match. There is still no live gene-synonym lookup — this is prompt-engineering only, and can still miss an alias the LLM doesn't recognize as non-canonical.
2. **Outcome side — semantic Factor resolution:** `scopeBiomarkerFactorSearch.js` (self-contained mirror of `biomarkerNetwork/biomarkerFactorSearch.js`, same pgvector endpoint `search.hugeamp.org/api/search/pgvector/biomarker-factors`) resolves the outcome text to real Factor IRIs by semantic similarity *before* querying — the same mechanism the Biomarker app's mechanism search already uses, per direct user suggestion. Hop 2 now queries a `VALUES` clause of these resolved Factor IRIs joined against the gene's `geneToFactor` edges, instead of blindly guessing a trait-label substring match (the old `factorByJoinQuery` strategy is kept only as a fallback when semantic search returns nothing). Hops 1 and 3 also benefit: the resolved factors' `cfde_disease` field is added to the trait-match candidate list alongside the raw outcome text, so a disease-level match can succeed even when the raw outcome phrase never would. All of this — the exact-match gene bug, the fix, and the new semantic hop-2 query — was verified against the live endpoint before trusting it (PDCD1 × resolved "interferon gamma" factors → a real, relevant hit: "Parasitic susceptibility and IFN-gamma (trait context: Vasculitis)", weight 0.18). This endpoint is Cloudflare-protected against non-browser requests (`curl` gets a JS challenge, a real browser tab does not) — verification used the Browser pane, not `curl`, for this specific check.

Coverage metadata gained a fourth output field, `resolvedFactors` (the raw semantic-search matches with scores), alongside `routes`/`coverage`, so the UI can show *why* hop 2 matched what it matched.

**Module C v0 UI wiring:** `ScopeKgEvidenceTable.vue` renders `findKgEvidence()`'s three routes as three small tables (one per route, own columns since edge shapes differ — direct: gene/trait/weight; factor: gene/factor/gene→factor weight/trait/trait→factor weight/matched-via/search-score; geneSet: gene/gene-set/trait/weight), plus the coverage line, plus a "Not found in ... for this route" line per route with zero edges rather than hiding it. This is explicitly a **transitional raw-data view**, not the final UI — the user is reviewing what the KG actually returns before deciding how to visualize the mini KG (as a graph, presumably); expect this component to be replaced, not extended, once that's decided.

Reached via a new welcome-panel option, **"Evaluate hypothesis + Search CFDE KG"** (`optionId: evaluateAndSearchKg`), reflecting that Module A's parse is a *prerequisite* for Module C here, not just build-order sequencing — Module C v0 has no independent way to get a target/outcome (no hub, no entity linkage), so it reuses whichever text Module A's `slots.target`/`slots.outcome` produced (value and resolved_id). `revealScope.vue`'s `onEvaluated()` checks a `kgSearchPendingAfterEvaluate` flag (set only by this combo option) and, once the evaluation resolves, calls `startKgEvidenceSearch()`. If either slot's `value` is `null` (Module A flagged it missing), the KG search does not run at all — `kgEvidenceBlockedReason` explains why rather than silently skipping or guessing a query from raw text. This is the concrete enforcement of "evaluation identifies the queryable elements before KG mining can run."

**Post-retrieval relevance triage (`scopeKgRelevance.js`):** running two real hypotheses through the full pipeline (2026-09-04) surfaced a problem the earlier fixes don't solve — results can be technically correct (right gene, real edges) but land in a tissue/disease context that has nothing to do with the hypothesis (a PD-1/cancer-immunotherapy hypothesis returned only autoimmune-disease associations; a hepatocyte/PGC-1alpha hypothesis returned only cardiomyopathy associations — this KG's genetic data for a given gene is often dominated by whichever disease happens to have the most GWAS studies, not the hypothesis's actual system). Research into a sibling component, `hybridSearchReveal.vue`, found it already solves the same two-axis problem (mechanism relevance vs. tissue/context relevance) via a post-retrieval LLM pass with "Hub Gravity Hijack" and "Site of Action Constraint" rules — `scopeKgRelevance.js`'s prompt adapts that pattern, reframed as **labeling, not rejection** (edges are annotated, never deleted — same "unscored" bounded-honesty philosophy as Module A).

`classifyKgEvidenceRelevance()` batches **every edge from all three routes into one call**, made once after `findKgEvidence()` fully resolves — not one call per route — so the model can weigh cross-route patterns (e.g. "every route points to the same unrelated disease") and apply one consistent threshold instead of three independently-drifting ones. Three labels: `on_topic` (mechanism and context both match), `same_domain_mismatched_context` (right gene/pathway family, wrong tissue/disease — e.g. the cardiomyopathy and autoimmune-disease cases above), `unrelated` (no plausible connection at all — expected to be rare in practice, since edges are already fetched by the *resolved* gene, so gene-level relevance is true by construction; genuine `unrelated` calls would come from a spuriously-matched intermediate factor/gene-set with no thematic tie at all).

**UI flow is explicitly staged, per user request** — this does not sit inside the KG-query progress overlay:
1. `findKgEvidence()` resolves → `ScopeKgEvidenceTable` renders immediately with unlabeled edges.
2. `runKgRelevanceTriage()` then runs in the background (`kgRelevanceLoading`, a small inline "Classifying relevance…" line under the coverage text — not the centered `ScopeProgressOverlay`, since the table is already visible and interactive).
3. On completion, `mergeRelevanceIntoRoutes()` non-destructively annotates each edge with `.relevance = {label, rationale}` and the table updates in place.
`runKgRelevanceTriage` guards against a race (captures `kgEvidenceAtStart` and bails if `this.kgEvidence` has changed identity by the time the classification resolves — e.g. the user reran evaluate or switched modules mid-triage).

**Prompt-tightening iteration, validated against live data:** an initial version of the prompt, tested against the real PDCD1 edge set above, produced an inconsistency — the exact same gene set (`WP_CANCER_IMMUNOTHERAPY_BY_PD_1_BLOCKADE`) appeared in two edges with different mismatched traits (Multiple sclerosis, Allergic disease) and got two different labels; the MS edge was upgraded to `on_topic` via a constructed rationale ("MS also involves T-cell dysfunction, where PD-1 blockade has therapeutic rationale") that stretched well past what the hypothesis actually claims. Re-ran both the PDCD1 batch (now uniformly `same_domain_mismatched_context`, no more split) and the PPARGC1A batch (unchanged, still uniformly `same_domain_mismatched_context`) against the live LLM endpoint to confirm the fix held without regressing the other case, before considering this done.

**"Search Biomarker KB" — a separate action, not a CFDE KG extension:** the sibling `biomarkerkg` graph (deferred at §6/Changelog 2026-09-04 as a future "expand" Action) is now built, but per explicit user direction it is framed and implemented as its **own** action, distinct from "Search CFDE KG," even though it starts from data Module C already resolved. Rationale (from the scoping discussion): it's a genuinely different KG with a different schema (plain direct triples, not RDF reification) and a different, two-hop-removed evidentiary relationship to the hypothesis (mechanism → shared-gene disease → biomarker, not a direct gene↔trait/factor edge) — collapsing it into "CFDE KG" would misrepresent how indirect this evidence actually is, which conflicts with the bounded-honesty principle (§1).

Mirrors `biomarkerNetwork.vue`'s own pipeline shape, per direct user description of the desired approach: mechanism (semantically-resolved Factor, already computed by Module C) → MONDO diseases sharing top-loading genes with that Factor → BiomarkerKB biomarkers linked to those diseases → LLM relevance triage. Two new backend modules:

1. **`scopeBiomarkerKbSparql.js`** — self-contained BiomarkerKB SPARQL client (same independence rule as `scopeKgSparql.js` — does not import the sibling `biomarkerNetwork/biomarkerKbSparql.js`). `listBiomarkersForDisease(diseaseIri, {limit})` queries the four disease-linking predicates (`OBCI_1000002/3/6/8` → diagnostic/monitoring/prognostic/susceptibility-risk) for one disease IRI at a time, always wrapped in `GRAPH <https://purl.org/okn/frink/kg/biomarkerkg>` — **confirmed live that an unscoped query times out** (30s, whole-store scan) while the same query with the `GRAPH` clause returns in under a second, so this is a hard requirement, not a style choice. Deliberately queries one disease per call rather than batching diseases via a shared `VALUES`/`LIMIT` — confirmed live that a single common disease (colorectal cancer: 10,000+ rows) would otherwise crowd out every other disease under one shared cap. This KG has no score/weight field to rank by at all — results are unranked; capped conservatively (`MAX_BIOMARKERS_PER_DISEASE = 8`) and left for the relevance triage to actually filter. Biomarker gene symbols are extracted from label text via a regex tied to this KG's `"... gene SYMBOL/NCBI:id"` label convention (confirmed live: naive substring matching on a gene symbol produces false positives, e.g. `"PDCD1"` matching inside `"PDCD10"` — the regex's `/NCBI:` boundary avoids that).
2. **`scopeBiomarkerBridge.js`** — `findDiseasesForFactor(factorIri)` mirrors `biomarkerNetwork/cfdeKgSparql.js`'s `listMondoDiseasesForFactor` (top-loading genes for a Factor → diseases those genes are linked to via `geneToTrait`, restricted to MONDO IRIs). `findBiomarkerBridgeEvidence({resolvedFactors, geneConfirmedFactorIris, onStep})` runs this for **all of Module C's already-resolved Factors** (user's explicit answer: "all 5 resolved factors," not just the top one), dedupes the resulting diseases by IRI across factors (keeping the max shared-gene count seen), sorts gene-confirmed diseases first then by shared-gene count, and caps to `MAX_TOTAL_DISEASES = 6` before the second-stage BiomarkerKB lookup — bounding round-trips regardless of how many factors/diseases stage one produces.

**Dropped design: an in-query gene-inclusion check.** The original plan was to check, inside the factor→disease SPARQL query itself, whether the hypothesis's target gene is among the genes shared with a candidate disease (user's explicit answer: "flag, don't skip" — never hide a disease for lacking the target gene, just label it). A first implementation added a `MAX(IF(...))` aggregate for this inside the top-N-genes-by-loading subquery — **verified live that this produced `false` for every single returned disease**, even for a factor where Module C's own hop 2 had already confirmed a real (if weak, weight 0.13) gene→factor edge, because that subquery's top-25-genes-by-loading cutoff doesn't guarantee a weak-but-real edge makes the cut. Rather than loosening the cutoff (which just moves the same problem), dropped the in-query check entirely and instead reuse `geneConfirmedFactorIris` — the set of factor IRIs where Module C's hop 2 *already* confirmed a real gene→factor edge, passed into `findBiomarkerBridgeEvidence` from `revealScope.vue` (derived from `kgEvidence.routes.find(r => r.id === "factor").edges`) — as the authoritative "gene confirmed" signal per factor. Strictly more precise: it checks the actual edge Module C already found, not an arbitrary top-N rank.

**`scopeBiomarkerRelevance.js`** — relevance triage, structurally identical in pattern to `scopeKgRelevance.js` (one batched LLM call over every biomarker across all disease groups, same three labels, same "annotate never delete" bounded-honesty rule, same race-guard via result-identity check in `revealScope.vue`). One deliberate, validated difference in rule 1: an exact match between the biomarker's extracted gene and the hypothesis's own target gene is treated as sufficient grounds for `on_topic` **even when the biomarker's disease context doesn't match the hypothesis's disease/system** — validated live (PPARGC1A hypothesis in a hepatocyte/HepG2 context; a PPARGC1A biomarker in a *Dilated cardiomyopathy* record correctly still classified `on_topic`, with the rationale explaining the gene-identity match carries the call despite the disease mismatch). This is intentionally **more permissive** than `scopeKgRelevance.js`'s stricter rule (added 2026-09-04 above) that a KG edge's trait must match the hypothesis's own disease even when the gene matches — the two prompts differ here because a BiomarkerKB record naming the literal target gene by an exact clinical-biomarker label is a stronger, more specific relevance signal than a statistically-inferred KG edge sharing a gene with an unrelated trait. **First live validation run surfaced the same class of over-eager upgrade bug already fixed once in `scopeKgRelevance.js`:** a biomarker whose disease context plainly did not match the hypothesis (cardiomyopathy vs. hepatocyte) was labeled `on_topic` with a rationale that explicitly acknowledged the mismatch and upgraded anyway — correct outcome for the exact-gene case per the rule above, but the prompt's original wording left room for the same failure mode on non-exact-gene cases too. Tightened rule 1's wording to explicitly require disease/system match *unless* the gene is an exact target match, and added a rule 4 (same gene + same mismatched disease must get the same label, mirroring `scopeKgRelevance.js`'s rule 5) before wiring this into the app, rather than waiting to find the inconsistency live again.

Live-verified the scale of the problem: one of the two test-bridge diseases used during earlier validation (MONDO_0005301) alone has **373** distinct biomarkers in BiomarkerKB, so the original cap was hiding 365 of them with no indication to the user. - The query itself was rewritten to `GROUP BY ?biomarker` with `GROUP_CONCAT(DISTINCT ?roleLabel; SEPARATOR=" | ")` for a `roles` field, mirroring `biomarkerNetwork/biomarkerKbSparql.js`'s exact `VALUES (?diseasePred ?roleLabel)` aggregation pattern — a biomarker asserted under multiple roles for one disease (confirmed live: APOA1 has both `diagnostic` and `prognostic` roles for MONDO_0005301) now renders as one row with `"diagnostic | prognostic"` instead of two separate near-duplicate rows.

With the cap now at 100/disease × up to 6 diseases, a worst-case run could ask the LLM to triage up to 600 items in one call — untested at that scale, and could become a real cost/latency/context problem in practice (unlike `biomarkerNetwork.vue`, which has no LLM triage step at all and so has no precedent for this trade-off). **Second, deeper fix to the same feedback (2026-09-04): the per-disease-grouped table itself was the wrong shape, not just under-capped.** After the fetch-cap fix above, the user shared a screenshot of `biomarkerNetwork.vue`'s actual biomarker table and pointed out two more things: (1) the "Biomarker" column there shows clean short names ("Cell adhesion molecule CEACAM5", "rs11540652"), not the long natural-language sentences SCOPE's table was showing; (2) the wanted shape is a single flat table with columns Biomarker / Associated gene / Roles / Diseases / Records, with triage columns added — not tables grouped per bridge disease.

Investigated why the labels differed and found a real, previously-unnoticed bug: `biomarkerNetwork.vue` actually uses a **different, more correct SPARQL traversal** than what `scopeBiomarkerKbSparql.js` had (both before and after the first fetch-cap fix). Confirmed live: the KG models a `?biomarkerRecord` node (the long-sentence assertion, e.g. "Increased expression of gene APOA1/NCBI:335") that links to a `?disease` via one of the four disease-relation predicates **and separately** links to the real `?biomarker` **entity** node (e.g. the APOA1 gene, or a dbSNP rsID node) via one of four distinct "entityRelation" predicates (`OBCI_1000009/15/16/17`). The entity node's own `rdfs:label` is the clean name; the record node's `rdfs:label` is the long sentence — these are two genuinely different KG-stored fields, not a client-side parsing distinction. `scopeBiomarkerKbSparql.js`'s query had been treating the record node as if it were the biomarker itself (`?biomarker rdfs:label ?biomarkerLabel ; ?diseasePred ${disease}` — no entity join at all), which is exactly why it only ever produced sentences. Also confirmed live: for dbSNP-based biomarkers, the entity node often has no `rdfs:label` at all, and `biomarkerNetwork.vue`'s own `biomarkerDisplayLabel()` method (`biomarkerNetwork.vue:1311-1317`) falls back to the IRI's last path segment (e.g. "rs10063294") in that case — ported this fallback verbatim as `biomarkerDisplayLabel()` in `scopeBiomarkerKbSparql.js`.

Fix, done as a faithful single-disease port of `biomarkerNetwork/biomarkerKbSparql.js`'s `listBiomarkersForMondoDiseases` (the function its UI actually imports and uses — that file also has an older, unused `listBiomarkersForDisease` function with the same wrong-node bug, not touched, since nothing in `biomarkerNetwork.vue` calls it):
- `scopeBiomarkerKbSparql.js`'s `listBiomarkersForDisease` rewritten to the `?biomarkerRecord ?diseaseRelation ?disease ; ?entityRelation ?biomarker` traversal, `GROUP BY` the entity (not the record), aggregating `roles` and `genes` (`GROUP_CONCAT`) and `recordCount` (`COUNT(DISTINCT ?biomarkerRecord)`) per entity — live-verified against MONDO_0005301 (clean names like "apolipoprotein A1" and correctly-aggregated multi-role rows returned).
- `scopeBiomarkerBridge.js`'s `findBiomarkerBridgeEvidence` now **merges** the per-disease-fetched results into one flat list deduplicated by biomarker entity IRI (a biomarker fetched via two different bridge diseases becomes one row with both diseases listed), matching `biomarkerNetwork.vue`'s single-table-across-all-diseases shape — while still doing one SPARQL call per disease (not one shared batched call), preserving the earlier fair-round-trip design decision. Returns `{ biomarkers, diseases, truncated }` instead of an array of per-disease groups; each biomarker carries `genes`/`roles`/`diseases` (pipe-joined strings + list forms), `recordCount` (summed across contributing diseases), `geneConfirmedAny`, and `viaFactors`.
- `scopeBiomarkerRelevance.js` reworked for the flat shape and for genes/roles/diseases now being **per-biomarker lists** rather than singular values (a biomarker can span diseases from different bridge factors) — rule 1's exact-gene-match language was updated from "the biomarker's disease" to "at least one of its listed diseases." Re-validated live after the rewrite: the same over-eager-upgrade case from the first validation (PPARGC1A exact-gene-match, disease mismatched) still correctly resolves to `same_domain_mismatched_context`, consistently across two near-identical inputs (rule 4 holds); a second live test even caught a genuine directionality mismatch (hypothesis says "overexpression", biomarker says "decreased expression") and correctly stayed conservative rather than upgrading on disease-name match alone.
- `ScopeBiomarkerEvidenceTable.vue` rewritten from grouped-by-disease sub-tables to one flat table — columns **Biomarker** (linked if the entity IRI is a URL, using the new `biomarkerDisplayLabel`-derived `displayLabel`) / **Associated gene** / **Roles** / **Diseases** / **Records**, then **Relevance** / **Relevance rationale** appended, plus a single `b-pagination` (`PER_PAGE = 10`) — directly matching `biomarkerNetwork.vue`'s table shape and pagination convention. A coverage line lists the bridging Factor label(s), associated-disease count, biomarker count, and the truncation notice.

**Third fix on the same thread (2026-09-04): user supplied the exact 4 network requests `biomarkerNetwork.vue` makes end-to-end (factor search, disease query, a third "shared genes" query this file didn't have at all, and the biomarkers query), decoded and diffed against this file's own queries.** Found three more real divergences beyond the label bug above, all fixed by porting the supplied queries exactly rather than re-approximating:

2. **A whole missing query stage: "shared genes."** `biomarkerNetwork.vue` runs a third query per factor — same top-25-genes-by-loading subquery as the disease query, joined via `VALUES ?disease {...}` against that factor's own resolved diseases, returning `(disease, gene, geneLabel, factorGeneLoading, geneTraitScore)` rows. 3. **Per-disease BiomarkerKB calls should have been one batched call all along.** The reference's biomarkers query passes **all** candidate disease IRIs into a single `VALUES ?disease {...}` block with one shared `LIMIT 100`, and includes `?diseaseCount` in the `ORDER BY` (biomarkers touching more of the candidate diseases rank first) — this codebase had instead queried BiomarkerKB once per disease and merged client-side, a design decision made specifically to avoid one large disease "crowding out" others' results (documented in the first 2026-09-04 fix above). Reversed that decision: switched `scopeBiomarkerKbSparql.js`'s `listBiomarkersForDisease` to `listBiomarkersForDiseases(diseaseIris, opts)`, a faithful multi-disease port including the `diseaseCount` column, and `scopeBiomarkerBridge.js`'s stage 2 to one call. The "crowding" concern turned out to be moot: since each row is one biomarker **entity** (not one disease-biomarker pair), a common disease only crowds proportionally to how many *distinct* entities it contributes, and diverging from proven, already-shipped production behavior wasn't worth it once actual production behavior was in hand rather than assumed.
